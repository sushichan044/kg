# ADR 0002: 特殊記法を方言別パーサーで正規化する

- Status: Proposed
- Date: 2026-08-04
- Issue: [#23](https://github.com/sushichan044/kg/issues/23)

## 文脈

小説投稿サービスと文書形式は、同じ見た目を異なる構文で表現する。
たとえば、pixiv は自己完結するタグを使い、カクヨムと小説家になろうは対象文字列の後ろにルビ区切りを置き、ハーメルンは入れ子にできる対タグを使う。
青空文庫には直前の文字列を参照する注記もあり、CommonMark、VFM、Re:VIEW はインライン記法だけでなく文書構造を持つ。

これらを一つのトークン列と文法へ統合すると、サービス固有の曖昧さ、エラー回復、拡張規則が共通パーサーへ漏れる。
一方、記法ごとに異なるデータモデルを公開すると、組版と表示が入力元ごとの分岐を持つことになる。

Issue #23 では、ルビ、太字、斜体、傍点を主な対象とする。
画像、参照、章分けは対象外とし、改ページだけは将来の組版制御として考慮する。

## 決定

公開拡張点として既存の `ManuscriptParser` を維持し、記法の方言ごとに独立したパーサーを実装する。
利用側は入力元または設定からパーサーを明示的に選び、自動判定は行わない。
ただし、`parseManuscript` で parser の指定を省略した場合は、記法を解釈しない `plainTextParser` を使う。
既定値は入力方言の推測ではなく、原文を変更しない安全な動作として扱う。

各パーサーは、構文解析、曖昧さの解消、エラー回復を所有し、結果を共通の `ParsedManuscript` へ正規化する。
正規化後の注釈は、見た目ではなくルビ、太字、斜体、傍点などの意味を表す closed union とする。
未知のタグ名、任意の CSS、入力元固有のタグをそのまま公開モデルへ通さない。

パーサー内部の構成は方言ごとに選ぶ。

- pixiv のような自己完結タグは、現在と同様に一方向の scanner で処理する。
- カクヨムは、直前の漢字列または `｜` と `|` で明示した親文字を `《読み》` と対応づけ、改行を越える候補と不成立の候補を原文として回復する。
- 小説家になろうは、丸括弧と二重山括弧で異なる読みの制約を持つため、カクヨムとは別の候補判定と回復規則を持つ。
- 青空文庫は、ルビ記法に加えて対象文字列を参照する注記を持つため、単純な後置ルビとは別に意味解決を行う。
- 入れ子可能な対タグは stack で処理する。
- 過去の文字列を参照する注記は、構文認識後の意味解決として処理する。
- CommonMark、VFM、Re:VIEW のような文書形式へ対応するときは、既存の準拠パーサーから得た AST を `ParsedManuscript` へ lower し、文法を再実装しない。

Issue #23 で追加実装する後置記法は、カクヨムのルビと傍点に限定する。
小説家になろうと青空文庫は将来の方言別パーサーを検討するための事例であり、この ADR は両形式の完全な対応を決定しない。

カクヨムのルビでは、終端記号まで対象範囲を確定できないが、一般的な文法上の backtracking は必要ない。
一方向の走査中に漢字列の開始位置と明示区切りの位置を保持すれば、`《` を読んだ時点で対象範囲を決定できる。
したがって、現時点では LL、LR、LALR などの解析方式、PEG のような文法形式、それらを実装する parser generator のいずれも共通基盤として導入しない。

AST から lower する adapter も、原文を変更せず、表示文字列と各書記素から UTF-16 の原文位置へ対応づけられなければならない。
adapter は、必要な原文位置を提供する準拠パーサーだけを利用する。
構文 node の原文位置を復元できず `ParsedManuscript` の契約を満たせない場合は入力全体を `Rejection` とし、その node を黙って除外したり、推測した範囲で公開したりしない。
これは、原文範囲を特定できる不正記法を本文として回復する場合とは区別する。

共通化するのは、UTF-16 cursor、行境界、原文から表示文字列と書記素への範囲対応、診断、正規化結果の構築といった文法に依存しない内部部品に限る。
lexer と parser の分離は公開契約にせず、複雑さが必要な方言の内部実装として採用する。

改ページを実装する場合は、文字範囲へ見た目を付与する `ManuscriptAnnotation` へ追加しない。
`pageBreak` を持つ別の closed union を `ParsedManuscript` に追加し、組版が消費する制御として表現する。
改ページ記法の原文範囲はタグを覆い、表示範囲と書記素範囲はゼロ幅とする。
collection の形式、同じ位置に複数の改ページがある場合の順序、組版が制御を適用する時点は、改ページを対象に含める設計で決定する。
その設計が決まるまで、`ParsedManuscript` に予約 field を追加しない。

公開モデルでは `ParsedManuscript` を「正規化済み原稿」、組版結果を「組版済み原稿」と呼ぶ。
AST と CST は各パーサーの内部表現と混同するため、公開モデルの呼称には使わない。

## 理由

方言別パーサーは、あるサービスの構文変更とエラー回復規則を、その方言の実装へ局所化する。
同時に、組版、校正、表示は入力元を知らず、正規化された意味と範囲だけを扱える。
ただし、正規化された意味や範囲の契約を変更すると、core、組版、校正、viewer の利用層へ影響する。

closed union は、新しい意味を追加するときに core、組版、viewer の対応漏れを型検査で検出できる。
任意タグを許す方式より拡張時の変更箇所は増えるが、未対応の見た目を黙って失うことを防げる。

## 影響

- サービスごとに parser object とテスト群を持つ。
- 同じ構文規則を複数のパーサーが必要とした時点で、規則ではなく cursor と範囲処理から共通化する。
- パーサー選択は frontend または呼び出し側の設定として保持する。
- 不正または未対応の記法は `Rejection` にせず、原文を保持した `ParsedManuscript` の成功結果と、記法の原文範囲を持つ診断を可能な範囲で返す。
- 新しい注釈種別は、意味、組版上の効果、viewer の表示方法を同時に定義できる場合だけ追加する。
- parser generator の導入は、手書き実装で線形時間の走査と局所的なエラー回復を維持できなくなった方言ごとに再検討する。

## 却下した案

### `PixivProvider` のような provider interface

解析は I/O や状態を持たない純粋な変換なので、provider より parser が責務を正確に表す。

### 一つの共通文法と共通 lexer

異なる構文体系の和集合を共通文法にすると、方言ごとの禁止事項と回復規則が条件分岐として集中する。

### 入力記法の自動判定

括弧、縦線、角括弧は通常の本文にも現れ、複数の方言で異なる意味を持つため、判定不能な入力を避けられない。

### 任意のタグを保持する汎用注釈

組版と viewer が未検査の文字列や見た目の指定を解釈することになり、正規化境界が失われる。

### 改ページを注釈として表現する

改ページは文字範囲の装飾ではなく、後続内容の配置を変える命令なので、注釈の範囲モデルと責務が一致しない。
